# ADR-0001 语言分工与演化路径 —— PY 增长原则 · 渐进迁移 · 新仓库重写远期选项

- **状态**：已采纳（2026-09）
- **关联**：`docs/task-orchestration-workflow-design.md` · `docs/dsh-生态共建规划.md` · `examples/aigility-platform/README.md`（工作流执行通道启用片段）
- **来源**：任务板工作流落地过程中引出的双栈边界讨论（py-bridge 动态 YAML / capability_node 异步限制 / 部署面 venv 依赖），以及"TS 侧是否需要/是否会被 Python 替代"的两轮架构推演。

## 1. 背景

本仓库是 TS 五域引擎（内核/契约/五域插件），AI 能力栈存在双轨：

- **aigility SDK**（PyPI `aigility`，独立仓库）：workflow（YAML → LangGraph）、RAG/检索/记忆等，经 py-bridge 声明式接入；
- **DSH 套件**（`@deepseek-ai/dsh`，TS/Cordis）：工具注册表、MCP client、web 工具、agent loop，经 dsh-interop 接入。

双栈并存带来三类成本：**部署面**（Python venv + 机器特定 py-plugins.json）、**边界细节**（init 固定 / 异步限制 / 序列化有损）、**双栈功能漂移**（认知/记忆/RAG 两边重复建设——长期最大税）。

## 2. 决策一：PY 增长原则 —— 新 AI 能力默认长在 Python

TS 侧增长收敛于平台脊柱，新 AI 能力默认经 py-bridge 声明式接入 Python（TS 零改动）。判据：

> **LLM 调用与流程控制在哪边跑都行（选部署成本低的）；AI 能力实现长在有生态的一边（Python）；平台工程长在宿主（TS）。**

| 留在 TS（平台脊柱，不可 PY 化） | 趋势向 Python（能力层） |
|---|---|
| 内核与契约：Seam / KernelAdapter / 热插拔 / DSH-Cordis | AI 能力实现：RAG / 检索 / 记忆 / 模型适配 / 复杂编排执行 |
| 入口与渠道：企微 / 飞书 / http-ingress / 静态托管 | 新 agent 能力原型与迭代 |
| 持久化与平台工程：PG（账号/审计/计量/积分/任务）/ 鉴权 | 生态依赖重的能力（LangGraph / 向量库 / 训练工具） |
| 编排**调度**：任务板状态机 / 执行器派发 / 人审闸门 | —— |

实证：aigility-workflow 经 py-bridge 挂入（TS 零改动）、py-plugins.json 声明式模型、capability_node 反向通道（Python 节点回调 TS Seam）——架构已为"新能力长在 Python"备好通路。判据的反向应用实例：STT 这类简单 glue 能力留在 TS（D3）即是合理的。

## 3. 决策二：工作流热路径的运行时选择

- 现状：任务板 `workflow` 执行器经 py-bridge 调 `aigility.workflow.runtime.run_yaml_workflow`（动态 config_path；每任务 new WorkflowEngine 为官方支持的低开销模式——构造只读 YAML、编译惰性、state_schema 可省）。
- 后续优化项（非现在）：D4 增加进程内 **TS YAML 运行器**（读同一份 YAML schema 的 llm_node + 条件边子集），消除热路径跨进程；**YAML schema 升格为跨语言契约**——同一份 YAML，Python LangGraph 跑或 TS 解释器跑，双运行时互为备份。
- 触发：延迟不达标 / 部署场景不允许 Python / 跨进程序列化成为瓶颈（见 §6）。

## 4. 决策三：演化路径谱系（按时间序，非互斥）

### 4.0 维持现状（默认态）

宿主 TS + 能力 PY，py-bridge 承载边界。本 ADR 的其余选项均为可选演进，不是承诺。

### 4.1 换法 B · 宿主瘦身（渐进迁移）

> 若未来团队决定把 TS 后端工程能力迁往 Python，采用四步渐进，每步独立可回退：

```
第一步：Python 侧起 FastAPI 服务，挂同一 PG、同一 token secret
        → 任务/审计/积分的 REST 契约原样平移（前端零感知）
第二步：LLM/工作流/RAG 能力本在 PY（litellm + LangGraph + py-bridge）
第三步：TS 收敛为「内核 + 契约 + 渠道 ingress + py-bridge」
第四步：工具面语言中立化（DSH 工具 → MCP server 形态，Python 经 MCP client 消费）
```

**迁移友好条件（已具备）**：业务数据全在 PG（task/audit_log/credit/llm_usage，无状态锁死在 TS 进程内存）；REST 是前后端唯一契约（前端零感知）；LLM/工作流/RAG 本就是 Python 强区。**薄 TS 宿主 + Python 能力**的形态有现成样板（examples/wecom-guide、wecom-timem）。

**难度分层**：任务 CRUD/CAS、审计、积分、鉴权（同 secret 验签）= 易；LLM/工作流/RAG = 本就在 PY；doc-worker（python-docx）/ MCP client = 中；DSH 工具套件 = 中-难（MCP 语言中立化路径）。

### 4.2 换法 A · 新仓库整体重写（远期选项）

> 在**新仓库**中以 Python 原生范式重写五域契约与引擎。注意：这不是对换法 B 的否定，而是其远期终点之一——**换法 B 是换法 A 的地基**（REST/数据契约的分离正是新仓库的立仓之本；先 B 后 A 才顺，A 不是跳过 B 的捷径）。

- **形态**：契约语义以**设计迁移**（五域依赖序、Seam 契约思想、热插拔与健康切换的范式），而非代码搬运；本仓（TS）转入维护直至退役；两个仓库长期共存亦可接受（aigility Python SDK 本就是独立仓库先例）。
- **触发信号**：Python 原生五域范式成熟并被验证（如 aigility workflow/能力层覆盖面追平）/ 团队与社区重心完全 PY 化 / TS 侧范式无演进动力。

### 4.3 明确不做（收窄后仅剩）

- 不在**本仓内**原地重写语言栈（若发生重写，在新仓库立项，即 4.2）；
- 不为语言统一提前迁移未触发的能力；
- 边界两侧不重复建设同一能力（现有例外：TiMEM 记忆 TS 接入 vs aigility memory——以引擎接入为准收敛）。

## 5. 反例约束（"尽量 PY"的边界，防走过头）

1. **热路径跨界调用是负收益**：高频、大 state 的路径不得跨 py-bridge 序列化（故有 §3 的 TS 运行器后手）；
2. **平台工程不得在 Python 重复建设**：鉴权/计量/审计/PG 已是 TS 资产，Python 侧要用走 Seam 反向通道（capability_node / seam_caller），不复制；
3. **Python 侧缺生产化渠道**：入口、多渠道输出、原型↔生产双形态全在 TS——PY 主化的极限是 aigility 独立成产品，而非 harness 被掏空。

## 6. 触发信号汇总（缺一不启动，出现即重议）

| 方向 | 触发信号 |
|---|---|
| 启动 TS YAML 运行器（§3 优化项） | 延迟不达标 / 部署不允许 Python / 跨进程序列化成瓶颈 |
| 编写 TS 版 aigility SDK | ① 交付场景明确"不能装 Python"（一体机/信创）；② TS 侧对 aigility 独有能力有真实需求且 py-bridge 边界成瓶颈；③ Node 生态出现付费集成需求 |
| 启动换法 B（宿主瘦身渐进迁移） | 团队 Python 工程师占比压倒性 / TS 侧维护困难 / aigility 独立产品化要求统一技术栈 |
| 启动换法 A（新仓库整体重写） | Python 原生五域范式成熟并被验证 + 换法 B 已完成 + 立项决策通过 |
| DSH 工具面 PY 化 | MCP 语言中立化成熟且 DSH 生态停止演进 |

## 7. 关联现状快照（2026-09）

- 任务板工作流执行通道：py-bridge + `run_yaml_workflow`（SDK 侧 runtime.py 由 SDK 侧排期，py-plugins.json 声明片段见 examples/aigility-platform/README.md——**runtime.py 落地前勿加声明**，py-bridge 任一 capability 初始化失败会拖垮插件 onLoad）；
- LiteLLM 本地代理为默认推理上游；失效的 platform:智谱行已停用（key 留存，修复后可热切回）。
