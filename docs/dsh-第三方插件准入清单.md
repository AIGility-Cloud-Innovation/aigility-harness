# dsh 第三方插件准入清单

> 日期：2026-09-30 ｜ 关联：[插件与应用安装体系设计](插件与应用安装体系设计.md) ｜ [dsh-升级影响评估-0.2.0](dsh-升级影响评估-0.2.0.md)
> 用途：第三方 DSH 插件的试用记录与准入台账——**给客户交付只装本清单内插件**；新插件走同一流程后追加。

## 准入流程（每次试用照此走）

1. **发现**：工具插件中心「社区插件发现」检索 / npm registry 核实（注意搜索索引可能超前实际最新版，以 registry packument 为准）；
2. **体检**：看 peerDependencies 的 cordis / dsh 服务版本范围是否覆盖本仓（套件 0.2.0-rc.2 + cordis 4.0.4）、repo 活跃度、有无 `!!js` 清单（有则不入）；
3. **安装**：`pnpm add -w <pkg>@<精确版本>`（根依赖，dsh-interop 解析链可达）→ 插件中心/API 装 row（DSH 插件包模式）；
4. **验证**：装载状态 loaded + 能力面确认（ctx.tools / 钩子 / 面板）+ 停用/再启生命周期；
5. **登记**：下表追加一行（版本钉死），客户预设（模块装配）按需引用。

## 已知缺口（后续增强）

1. **安装 API 的 DSH 模式缺「自动 pnpm add」**：当前 DSH 插件包需先手动 `pnpm add -w` 再装 row（MCP server 模式无此问题——走 npx 命令）。增强方向：安装 API 检测包不在 node_modules 时自动 `pnpm add -w`（或前端明确提示两步）；
2. **npm 搜索索引与 registry 实际版本有偏差**（notify 0.3.8 搜索可见、实际 latest 0.3.7）——社区发现面板的版本号以 registry packument 复核为准；
3. time-machine / notify 的能力面不在 ctx.tools 工具桥（钩子/通知形态），「装了什么」的可观测性靠 dshStatus 装载态——后续可在已安装插件面板展示插件声明的 provides。
