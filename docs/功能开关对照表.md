> 排查时间：2026-10-27 · 纯只读排查，未改任何配置
> 目标服务：`aigility-feishu-task-loop.service`（systemd，PID 2123172）
> 目的：回答「哪些功能开着、凭什么开着」

---

## 一、核心结论（先看这个）

| 结论 | 说明 |
|------|------|
| **服务配置里只显式写了 2 个变量** | `NODE_ENV`、`WORKER_TEAM_TIMEOUT_MS` |
| **其余功能开关全靠「代码默认值」开着** | 代码里判定方式为「**除非显式设为 0/false/off，否则开**」 |
| **因此：这些功能现在确实是开着的** | 不是"没配就没开"，而是**默认开启** |
| **风险点** | 想关掉某个功能时，**服务文件里找不到对应开关**，容易误以为控制不了 |

一句话：**当前功能都是开的，且是靠代码默认值开着的 —— 服务配置文件里看不出来。**

## 三、当前进程实际环境（实测）

对运行中进程（PID 2123172）读取环境变量的结果，**业务相关项仅有两个**：

```
NODE_ENV=production
WORKER_TEAM_TIMEOUT_MS=3600000
MODELARTS_API_KEY=<redacted>
```

> 其余全是桌面会话继承变量（`DISPLAY`、`QT_*`、`GTK_*`、`SSH_*` 等），
> 与本服务功能无关。

**这就是问题的直观体现**：进程环境里**看不到** `TASK_STATE_SCAN`、`OBSTACLE_ANALYST`
这类开关，但它们的功能**确实在跑** —— 因为代码把「未设置」判定为「开启」。

## 四、这意味着什么（风险）

### 风险 1：想关功能时找不到地方
有人想把"状态队列扫描"关掉，翻遍服务配置发现没有 `TASK_STATE_SCAN`，
可能误判为"这功能没法关"或"根本没这功能"。实际解法是**主动加一行**：

```ini
Environment=TASK_STATE_SCAN=0
```

### 风险 2：看配置会得出错误结论
只看服务文件，会以为这服务只跑"工人超时控制"，而实际上
**任务扫描、障碍分析、工人驱动循环全都在运行**。

### 风险 3：默认值变更无人知晓
如果哪天代码把某个默认值从"开"改成"关"（或反之），
**服务配置毫无变化，但行为变了** —— 因为真源在代码里不在配置里。

## 五、建议（待你决定，未执行）

### 建议 1：把关键开关显式写进服务配置

让"配置即真相"，避免"代码默认值黑箱"。建议至少显式化这几个：

```ini
[Service]
Environment=NODE_ENV=production
Environment=WORKER_TEAM_TIMEOUT_MS=3600000
# ── 以下为显式化（值同当前默认，仅把真相写进配置）──
Environment=TASK_STATE_SCAN=1
Environment=WORKER_TEAM_INTERVAL_MS=60000
Environment=OBSTACLE_ANALYST=1
```

**好处**：看配置就知道跑着什么；想关就改这一处；默认值变化不会偷偷影响行为。
**风险**：**极低** —— 写的值与当前生效值完全相同，行为不变。

### 建议 2：长期 —— 配置真源化

按《服务保活设计》第三步，引入 `config/services.yaml` 作为唯一真源，
systemd unit 由它生成。这样"生效值来自哪里"永远可回答。

### 建议 3：给 agent 的健康快照里带 `source` 字段

```json
"config_effective": {
  "TASK_STATE_SCAN": { "value": "1", "source": "default" },
  "WORKER_TEAM_TIMEOUT_MS": { "value": "3600000", "source": "service-file" }
}
```

## 六、附：开关命名规律（便于以后自查）

本次排查发现代码里的开关遵循统一模式：

```
值 ∈ {0, false, off}  → 停用
其他（含未设置）      → 启用
```

**这意味着：`未设置 = 开启`**。所以「服务配置里没有」**不等于**「功能没开」，
而恰恰等于「功能开着，但控制权在代码默认值手里」。

以后要确认某个功能是否在跑，**不能只看配置文件**，要么查代码默认值，
要么看运行日志（如驱动循环启动那行）。
