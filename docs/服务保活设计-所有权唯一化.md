# 服务保活设计 —— 所有权唯一化

> 撰写：2026-10-27 · 状态：设计定稿，第一步已落地（`managed-apps.json` enabled=false）
> 起因：feishu-task-loop 出现 **140+ 次无限重启风暴**，同一服务的多套保活机制互抢锁

---

## 一、问题：谁在保活？——四方打架

2026-10-27 实测发现，`feishu-task-loop` 这一个服务，同时有 **四套机制** 认为自己该管它：

| # | 托管者 | 当时的实际行为 | 结果 |
|---|--------|---------------|------|
| 1 | `aigility-feishu-task-loop.service`（systemd） | `Restart=always`，锁定唯一实例 | **正牌保活者** |
| 2 | 平台 `managed-apps.json` | `enabled: true`，启动时去 spawn 同一服务 | 抢锁失败 |
| 3 | 平台 `task-loop-manager` | HTTP API 提供 start/stop/restart | 抢锁失败 |
| 4 | 人工 `tsx` 直启（本次排查中发生） | 抢到锁并持有 | 让 systemd 永远抢不到 |

**现象**：systemd 每 2 秒重拉一次，每次因抢不到锁 `exit 1`，累计 **140 次**，且无上限、无告警。

```
● activating (auto-restart)  ← 永远到不了稳定的 running
  NRestarts=140
  Process: ExecStart=...tsx src/index.ts (code=exited, status=1/FAILURE)
```

### 根因（一句话）

> **flock 只防「重复启动」，不防「多个托管者都以为自己该管」。**

锁解决的是"同一时刻不能有两个实例"，但今天的问题是 **四方都认为自己有资格启动**——每个都按自己的逻辑去抢锁，抢不到就重试，从而形成风暴。

### 次生问题：平台的健康检查「凭记录判活」

平台日志里有一句误导性极强的记录：

```
[managed-apps] feishu-task-loop 已在运行 (pid=1494441)，跳过拉起
```

而该 PID **早已不存在**。平台是"读配置文件里记的 PID"来判断存活，而不是"真的去验活"。于是死进程被当成活实例，平台以为自己不需要管——**记录与事实脱节**。

### 次生问题：systemd 无限重试无退避

```ini
Restart=always
RestartSec=10     # ← 只有这个，没有启动限流
```

缺少 `StartLimitIntervalSec` / `StartLimitBurst`，故障时表现为 **疯狂重试、静默掩盖**，而不是 **停下报警、等人处理**。

## 二、设计原则

### 原则一：保活权必须唯一

> **谁保活，谁就是唯一所有者。观察者永远不能变成所有者。**

一个服务在同一时刻 **只能有一个** 保活者。其余所有组件对该服务只有 **读** 权限（状态、日志、配置），想要产生影响必须走"所有权转移"流程。

这条原则直接消灭今天的问题类别：不允许"两套保活机制并存"。

### 原则二：状态必须「验活」，不能「读记录」

```
❌ 反例：查配置里记的 pid=1494441 → 判"已在运行"
✅ 正解：pidAlive(pid) && /proc/pid/cmdline 匹配预期 && 锁属于该 pid → 才判 running
```

三条同时成立才算活着：**进程在 + 是对的进程 + 持有锁**。任一不成立即为 `stale`，需要处理。

### 原则三：配置单一来源，且必须能回答「这个值从哪来」

今天排查时最大的障碍是：**service 文件里没写某个开关，那它到底生效没有？**

无法判断 → 只能猜。所以设计上要求每个生效配置项都带 **来源标注**：

```json
{
  "WORKER_TEAM_INTERVAL_MS": { "value": 60000, "source": "default" },
  "WORKER_TEAM_TIMEOUT_MS":  { "value": 3600000, "source": "service-file" },
  "TASK_STATE_SCAN":         { "value": "1", "source": "env" }
}
```

`source ∈ {default, env, service-file, ui-override}`。**这一栏是给 agent 和用户最有价值的信息**——一眼看出"到底是谁定的这个值"。

### 原则四：给 agent 的是结构化上下文，不是原始日志

不要把 4.8 万行日志丢给 agent。应该提供一份 **服务健康快照**：

```json
{
  "service": "feishu-task-loop",
  "owner": "systemd",
  "health": {
    "state": "running",
    "uptime_s": 1420,
    "restarts_1h": 0,
    "last_exit": { "code": 0, "at": "2026-10-27T01:25:00Z" }
  },
  "config_effective": { "...带 source..." },
  "alerts": []
}
```

**agent 只需这份快照就能判断"是否健康、要不要干预"**，需要细节时再按需拉取日志。

### 原则五：故障要「停下来报警」，不要「疯狂重试」

保活机制必须带 **启动限流**：短时间连续失败若干次后，停止重试并进入 `failed` 态 + 告警。

> 疯狂重试会掩盖问题、污染日志、干扰同机其他服务。**宁可停在一个显眼的 failed，也不要静默地转 140 圈。**

## 三、推荐架构

```
┌─ systemd（唯一保活者）────────────────────────┐
│  aigility-*.service  × N                     │
│  · Restart=always + 退避 + 启动限流            │
│  · 崩溃自愈 / 开机自启 / 资源限制 / 日志归集     │
└──────────────────┬───────────────────────────┘
                   │ 读写同一份声明式配置
┌──────────────────▼───────────────────────────┐
│  aigility-platform（配置与观测面，无保活权）    │
│  · UI 改配置 → 写 config → systemd reload     │
│  · 只读 status / logs / health                │
│  · 绝不自己 spawn 进程                         │
└──────────────────────────────────────────────┘
```

### 为什么保活放在 systemd，而不是平台自己 spawn？

| 方案 | 保活能力 | 问题 |
|------|---------|------|
| 平台 spawn 子进程 | 平台死则服务死 | 平台自身还需被保活 → **套娃**；且正是本次冲突源 |
| 纯 flock 互抢 | 无保活保证 | 本次 140 次风暴的直接原因 |
| **systemd 独占** ✅ | 最强（自愈/自启/限额/日志） | 需一次性理清所有权 |

systemd **天然就是保活层**，平台不该重复实现它。今天的教训恰好证明：两套保活并存 = 互相踩踏。

### 配置流转

```
用户 UI 改配置
   ↓
写 config/services.yaml（唯一真源）
   ↓
生成 systemd unit（模板化）
   ↓
systemctl --user daemon-reload && restart
```

**绝不允许出现**"服务文件里没有、代码默认值却开着"的模糊态——所有生效值都必须能从真源推导出来。

## 五、落地步骤

### 第一步：切断冲突源（✅ 已完成 2026-10-27）

`config/managed-apps.json` → `enabled: false`

```json
{
  "name": "feishu-task-loop",
  "enabled": false,
  "_note": "保活所有权归 systemd（aigility-feishu-task-loop.service）。平台不得再拉起同一实例，否则两套保活机制互抢 flock 会造成无限重启风暴（2026-10-27 实测 140+ 次）。"
}
```

让平台不再试图拉起 loop，所有权明确归 systemd。**一条改动即根除冲突**。

### 第二步：给 systemd 服务补启动限流（待办）

```ini
[Service]
Restart=always
RestartSec=10
StartLimitIntervalSec=300
StartLimitBurst=5
```

效果：5 分钟内失败 5 次就**停下**，进入 `failed` 等人工，不再无限重试。

### 第三步：平台改纯观测面（要做 UI 时）

- 状态/日志/配置 **全部只读**
- 写操作一律转为"生成 systemd 配置 + reload"
- 提供第三节定义的 **服务健康快照** API 供 UI 与 agent 消费

### 第四步：配置真源化 + 审计

一份 `config/services.yaml` → 生成各 systemd unit；UI 变更走审计日志。

## 六、验收标准

- [ ] 任一服务在任意时刻 **有且仅有一个** 保活者
- [ ] 非所有者组件 **无法** 通过任何路径启动该服务（代码层拦截，非靠自觉）
- [ ] 健康状态判断 **基于验活**（进程 + cmdline + 锁），不基于记录
- [ ] 每个生效配置项都能回答 **"这个值从哪来"**（`source` 字段）
- [ ] 故障在有限次重试后 **停下并告警**，不无限重试
- [ ] agent 可通过一份 **结构化快照** 判断服务健康状况，无需读原始日志
