# AI 治理路线图 —— aigility-harness 研发路线图

> **状态**：v1.0（2026-09-27）
> **定位**：aigility-harness 是一套「AI 治理 Harness」——五域架构回答「AI 能力怎么组织」，本路线图回答「**凭什么放心让 AI 干活**」：各治理能力在什么阶段、以什么功能形态落地、按什么标准验收。

## 一、治理口径：五支柱

「治理」不是独立模块，而是对全部五域能力的**横向约束**。本文所有阶段规划都挂在这五根支柱上：

| 支柱 | 回答的问题 | 现有落点 |
|------|-----------|---------|
| **收口 Ingress** | 外部信号是否只能走唯一入口，不存在旁路？ | D1 ingress 唯一收口（http / 企微 / 飞书）；旁路即缺陷 |
| **授权 Authz** | 谁能用哪个能力 / 应用 / 模型？ | 平台账号 + 两权分离 + API Key；网关主密钥仅服务端持有 |
| **闸门 Gate** | 高风险动作是否被判定、复核、隔离后才执行？ | 任务三段式判定、Plan 拆解 → YAML 人审、沙箱、工人验收契约 |
| **可审 Audit** | 每笔调用是否可计量、可追踪、可回放？ | audit_log、按用户·模型·日 Token 计量、积分账务、traceId 全链路、degraded 显式标记 |
| **可换 Replaceable** | 实现替换是否动摇治理契约？ | Seam 契约（契约是主体，插件是过客）、dsh 可替换承诺、py-bridge 声明式边界、PG 单库多职三契约可换 |

五域在治理中的角色分工：

| 域 | 治理角色 |
|----|---------|
| D1 底座 | **执法部门**——入口收口、鉴权限流、审计计量、总线与队列 |
| D2 认知 | **供应商管理**——只供算力不载业务，降级必须显式标记 |
| D3 行动 | **高风险作业区**——强隔离强沙箱，工人产出受验收、汇回主人格署名交付 |
| D4 编排 | **审批流**——任务判定、规划、人审闸门、派发控制 |
| D5 人格 | **代言人**——主人格唯一、对用户负责；不实现能力只声明与委托 |

## 四、各阶段功能规划

### 阶段 G0 · 治理基座（✅ 已达成）

入口唯一收口、平台账号 + 两权分离、审计计量积分、stub 降级 + traceId 全部就位，五域原型闭环（`pnpm example:prototype`）与产品装配（AppBase / FDE 工作台 / 智悦平台）可用。明细见 §二 盘点表，此处不再展开。

### 阶段 G1 · 治理闭环（🔶 当前阶段）

主题：把「已设计未实施」「已验证未声明」「已立契约未显式化」的治理件收尾，让治理链条**端到端闭合**。

**G1-1 工作流执行通道转正** ⏳
- 内容：aigility SDK 侧 `aigility.workflow.runtime.run_yaml_workflow` 落地后，在 `config/py-plugins.json` 的 aigility-workflow 插件追加 `@orchestration/workflow-runtime` 声明（声明片段已备好，见 examples/aigility-platform/README.md）；任务板「批准执行」从优雅失败转真执行。
- 约束：runtime.py 落地前**勿**提前声明——py-bridge 任一 capability 初始化失败会拖垮插件 onLoad（该脆弱点由 G1-4 治理）。
- 验收：任务板复杂任务 → Plan 拆解 → 生成 YAML → 人审批准 → py-bridge 真跑 → 结果回写任务板。

**G1-2 人审闸门契约化（审批服务立项）**
- 内容：把任务板的「YAML 人审」抽象为 D4 可复用的**审批闸门契约**（pending → approved / rejected，全程审计留痕），落为 layer-orchestration 通用能力；aigility-platform「待办审批」区块从 Mock 接真（该页当前明确标注「引擎无审批服务，待立项」）。
- 原则：任何「LLM 产出 → 执行」路径都可声明「执行前须人审」，闸门在编排层统一收口，不在各业务插件散落实现。
- 验收：任务板工作流与新接入路径共用同一闸门契约；拒绝路径有审计记录且任务不派发。

**G1-3 manager 按应用授权实施** 📐
- 内容：照 app-permission-design.md §3 规格执行（`app_members.role` 列 + manage 块单点放宽 + 前端标注，半天量级）。
- 触发条件（已记录在案）：出现「第二个人需要管理非本人创建的应用」的真实需求。aigility-platform / 备课夹复用 AppBase 底座后此场景已现，建议本阶段内实施。
- 验收：设计文档 §4 七条验收清单逐条过，审计日志出现 `app.member.role`。

**G1-4 py-bridge 初始化故障隔离**
- 内容：单个 capability 声明失败不再拖垮插件 onLoad——跳过该 capability、发告警事件、Seam 上标记不健康交 scheduler 处理，其余能力照常服务。
- 验收：py-plugins.json 加入指向不存在函数的 capability → 启动不瘫、管理面可见该能力告警；既有 7 例端到端测试回归全绿。

**G1-5 工人验收判定显式化**
- 内容：D3 工人契约的「受验收判定」环节给出统一最小实现——产出完整性校验（非空 / 格式 / 声明的文件真实存在）+ 降级产物强制携带「模板降级」标记（循教师备课夹铁律）+ 验收结果写审计。doc-worker 已有雏形，契约上升入 core，编码工人（codex / zcode / claude）接入。
- 验收：工人产出空壳 / 假成功时，主人格收到显式失败并可复述原因，而不是署名交付空壳。

**G1-6 已验证 Python 能力按需收编**
- 内容：`@cognitive/memory`、`@cognitive/rag-retrieval`、`@orchestration/chat-flow` 三项 aigility 能力已验证但未声明进 py-plugins.json（README 8.3 ⚠️ 项）；在 G1-4 完成后按场景需求逐项声明。pgvector（`PgVectorStore` 已实现）作为知识库 / 向量检索场景（policy-agent §五等）的 harness 侧依赖同步就位。
- 验收：任一声明项经 Seam 调用端到端可用，且初始化失败不拖垮插件（G1-4 保证）。

### 阶段 G2 · 生产级治理

主题：从「原型可用」到「可交付企业部署」。承接 README §十阶段 3/4/5 的全部缺口，按治理优先序排列。

**G2-1 载体真隔离（Subprocess / Daemon 真拉起与守护）** —— README 阶段 3 缺口
- 内容：`CarrierManager` 补齐真 Subprocess / Daemon 载体与 restart（载体级重载）；`layer-action` / `layer-persona` / `py-bridge` 已声明的 `preferredCarrier: Subprocess` 从静默降级转真。
- 优先序：D3 行动域先行（编码工人、doc-worker——高风险高副作用，最需要崩溃隔离）→ py-bridge（Python 子进程本就独立进程，验证载体抽象）→ D5 人格守护进程化。
- 验收：杀掉工人子进程，主人格收到健康告警并自动重启或降级，用户侧表现为「失败可解释」，而非整个进程全挂。

**G2-2 指标采集 + 熔断器** —— README 阶段 4/5 缺口
- 内容：scheduler 探测数据（延迟 / 失败率 / 负载）落 PG 指标表，供 rebind 决策与用量看板消费；熔断器契约入 core、实现入 D1，挂 LLM 上游调用与工人调用两处。
- 验收：上游连续失败 → 熔断打开（快速失败且带降级标记）→ 半开探测恢复；rebind 决策引用真实指标而非单纯连续失败计数。

**G2-3 统一追踪后端（OTel）** —— README 阶段 5 缺口
- 内容：traceId 已进程内贯穿，补 OTel exporter 与跨进程 context 透传（随 G2-1 载体打通）。与 DSH `session-telemetry-otel` 行的关系：只采纳自托管后端方向，遥测外传保持默认关闭的既有基线。
- 验收：一条跨「入口 → 人格 → 编排 → 认知 → 行动 → py-bridge」的调用，在追踪后端可完整回放。

**G2-4 跨进程副作用回收** —— README「DSH 补齐清单」#4
- 内容：`ctx.effect` 副作用可逆机制扩展远端形态：远端资源释放、硬件复位、连接销毁。
- 验收：终止载体进程后，其持有的沙箱目录 / 临时文件 / 子连接被回收或标记待回收，不产生孤儿资源。

**G2-5 系统性安全加固** —— README 阶段 5 缺口
- 内容：① 越权判定——policy-agent 模块 8 的 harness 侧通用化：授权清单（章程 / 权限矩阵）入库后，行动域高风险操作做越权比对；② 密钥托管统一——评估把 DSH `.credentials.yaml` 托管凭据模式（前端不回显）推广到全部 ingress / 出口插件；③ 依赖与构建白名单（allowBuilds 先例）纳入定期审计。
- 验收：无密钥回显路径；高风险操作清单化且越权可判定；审计可回答「谁在何时让哪个工人对哪个仓库做了什么」。

**G2-6 租户与权限矩阵接真**
- 内容：aigility-platform「租户 / 权限矩阵」从 Mock 接真（RBAC 服务立项评估；底座复用 app_members.role + 应用授权体系）；白标 branding 已有，补租户计费接真。
- 验收：租户 A 的成员 / 用量 / 积分与租户 B 完全隔离，且管理员可按租户出账。

### 阶段 G3 · 生态与双形态治理

主题：治理语义随插件进入 dsh 生态；原型↔生产双形态切换闭环。

**G3-1 dsh-plugin-* M3** —— 照 dsh-生态共建规划 §四/§七：角色族 + app-dev + timem-task 插件化；metering 挂接 `dsh-token-meter`（**治理语义随插件带进官方 dsh**：计量/审计在官方会话中同样可核算）；npm 首发 + 生态 demo。

**G3-2 dsh-plugin-* M4** —— 数据空间 + installer 插件化；评估「开发者发行版」。治理基线（遥测默认关闭、`!!js` 白名单、锁版本）作为发行版**准入项**而非可选项。

**G3-3 NetworkService 载体 + NATS 桥** —— README 阶段 3/4 缺口：「DSH 补齐清单」#1 的 Seam↔NATS 双向协议转换落地；健康事件出 NATS；跨机 failover。至此「四载体抽象」四态齐备，原型↔生产双形态具备全量切换能力。

**G3-4 状态迁移系统** —— 「DSH 补齐清单」#6：记忆、会话、人格跨实现迁移。验收线：同一套业务代码在 InMemoryKernel（原型）↔ kernel-dsh（进程内生产）↔ 分布式装配（NetworkService 生产）三形态间切换零改动，三形态冒烟入 CI。

### 阶段 G4 · 自治与演化（远期，触发条件制）

**G4-1 TS YAML 运行器** —— ADR-0001 §3 的优化后手：**仅当**延迟不达标 / 部署不允许 Python / 跨进程序列化成为瓶颈时启动；同一份 YAML schema 双运行时（Python LangGraph / TS 解释器）互为备份，schema 升格为跨语言契约。

**G4-2 全维自动热替换** —— 负载 / 显存 / 故障指标驱动的运行时无感切换扩展到跨机；每次 rebind 决策带审计记录与决策依据（可回答「为什么切换」）。

**G4-3 治理策略即代码** —— policy-agent 的制度审查能力反哺 harness 自身：阈值 / 权限 / 预算 / 降级策略从散落的 env 与代码收敛为**声明式策略文件**（policy-kb 模式：规则打底、变更留痕），策略变更本身走 G1-2 审批闸门。

**G4-4 语言演化触发评估** —— 严格按 ADR-0001 §6 触发信号表重议（TS YAML 运行器 / TS 版 aigility SDK / 换法 B 宿主瘦身 / 换法 A 新仓库重写 / DSH 工具面 PY 化）。本路线图**不预设结论**，只承诺触发即评估。

## 六、明确不做

1. **不为治理而治理**——每项治理能力必须有真实触发场景才实施。先例：manager 角色设计定稿后挂起，等触发出现再实施（半天量级，随时可启）。
2. **不自研 LLM 网关**——LiteLLM 已承担路由 / fallback / 限流；仅当交付场景强制（一体机 / 信创不能装 Python 之外的新约束）才重议。
3. **不在 PG 之外引入新中间件**——除非对应契约（BusBridge / TaskQueue / VectorStore）的更换原则被真实部署触发。
4. **不预设语言迁移时间表**——ADR-0001 触发条件制，本路线图不排日历。
5. **治理不牺牲原型速度**——G2 前所有治理件在原型模式必须可跳过（Profile 区分）；治理的代价只在生产形态收取。
