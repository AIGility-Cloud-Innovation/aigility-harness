## 〇、五条基线决策（2026-09-30 用户拍板，本文的公理）

1. **通道绑定是可选的**：并非所有角色都出现在 IM——纯网页角色、纯后台角色没有 channels 段，照样是完整角色；
2. **面貌 = 本体（一角色一 app/平台）**：角色一旦绑定某平台 app，其在该平台的头像/名字必须与角色本体一致——身份一致性是**要求**而非权衡；
3. **跨位置 = 同一角色**：网页（内勤）与 IM（外勤）是同一角色的不同出现位置——同一个人格、同一份记忆、同一个岗位；渠道只是 presence；
4. **跨平台 = 同一个人的多个账号**：同一角色可以在飞书、企微、任何其他平台聊天——同一个人在不同平台创建的账号；多平台不是多角色，记忆域随角色唯一；
5. **对端人员同样跨平台归一，且页面可配**：同一个「人」跟角色对话时，跨平台归集为同一 Memory Subject（TiMEM user_id）；**已实施**——`timem-team-registry` 登记表 + IdentityPage 审查页（详见 [项目小助理-数据对齐与记忆设计](项目小助理-数据对齐与记忆设计.md)），本文增量仅补 wecom/web 两条身份轴（§四·补）。

## 〇·补、所有权模型（2026-09-30 用户拍板）

**角色包机制与公共角色归 harness 项目；各网站（智悦/fde-workbench/…）是消费方，将各有自己的维护者。**

| 层 | 归属/维护者 | 内容 |
|---|---|---|
| 机制层 | harness 项目（平台/框架维护者） | 角色包**格式规范**（SKILL.md + role.json）+ **共享加载器** `@aigility-harness/role-kit` + **公共角色目录** `<repo>/roles/`（公共角色事实源）+ appbase 底座原语 |
| 站点层 | 各站维护者 | 站点私有角色（`examples/<site>/roles/`，同 id 站点优先=定制权）+ 自己的编辑器（智悦工厂是一个编辑器实现，非事实源）+ 消费（ingress/会话/记忆执行） |

- 解析顺序：站点私有 → 公共（role-kit 双层解析, 同 id 站点赢）；
- 人员-身份绑定不进包（组织/隐私资产, 留平台侧 identity-registry）；
- **R1 已落地**：`packages/role-kit`（加载器 + 5 测试）+ `roles/README.md`（格式规范）+ `roles/harness-guide/` 首个公共角色包样板（自 layer-persona 外置, 代码常量降级为兜底）。

## 一、角色五要素 = 五域声明面（采纳）

一个角色最该清楚自己的准确定位——五要素逐项映射到五域的声明与执行：

| 五要素（归角色声明） | 域 | 执行（归平台收口） |
|---|---|---|
| **自己是谁** | D5 人格 | persona 注册表 + 技能 system prompt（已真）；**跨位置唯一**（基线 3） |
| **数据从哪里来** | D1 订阅 + TiMEM | 平台聚合拉起通道连接；数据资产绑定（alarm_log/知识库/图谱）走既有数据面 |
| **要做什么动作** | D3/D4 | 工具委托（MCP/技能）+ 复杂任务走编排（executor-dispatch 同款） |
| **消息发到哪里去** | D1 出站 | 回复走原通道；主动播报群由平台统一推送（计量/审计归集） |
| **展示什么面貌** | D5 展示 | **IM 面貌 = 角色本体**（一角色一 app，基线 2）；网页面貌 = 平台 UI 的角色呈现 |

原则沿用 D5 既有表述：**角色只声明与委托，不持有连接与凭证**——这是「声明归角色、执行归平台」的分界线。

**presence（出现位置）模型**（基线 3/4 的落地）：一个角色可以有零到多个 presence——
- `web`（内勤）：平台对话工作台/市场页/应用内的角色对话——**无需 app**，走平台既有的 persona 路由；
- `im:feishu` / `im:wecom` / `im:<其他平台>`（外勤）：每个平台一个面貌一致的平台管理的 app；同一角色跨任意多平台（基线 4）；
- 共享：人格（persona/技能 prompt）、记忆（TiMEM agent_id 按 role.id 归集，**网页+全部平台同一记忆域**）、岗位（工具/技能/编排委托）。

## 二、角色 manifest（roles.json → v2）

在现有 roles.json（群/私聊 → persona + skills + mcp）基础上补齐五要素；**channels 段可选**（基线 1）：

```yaml
role:
  id: baojing-analyst
  identity:                      # 我是谁（跨位置唯一）
    name: 报警研判助手
    prompt_ref: skill:baojing-analyst
  sources:                       # 数据从哪里来
    channels:                    # 可选：不绑定 IM 的角色省略此段（基线 1）；同一角色可跨多平台（基线 4）
      - im:feishu:
          app: feishu-baojing    # 面貌=角色本体（app 注册信息按角色配置, 基线 2）
          chats: [oc_xxx]
          mention_only: true
      - im:wecom:
          app: wecom-baojing     # 同一个人在企微的账号（基线 4）
          chats: [wr_xxx]
    data: [ alarm_log, neo4j:baojing-graph ]
  actions:                       # 做什么动作（委托）
    tools: [ mcp__neo4j__read_neo4j_cypher, skill:baojing-analyst ]
    workflows: [ executor-dispatch ]
  outbound:                      # 消息发到哪里去
    reply: same-channel
    push: [ im:feishu:oc_yyy ]   # 主动播报群（task-loop 的播报能力即此类）
  memory:                        # 跨位置/跨平台共享（基线 3/4）：全部 presence 同一记忆域
    agent_id: baojing-analyst    # TiMEM 按 role.id 归集, 不按渠道/平台分裂
```

## 三、平台聚合执行（bot 层的消亡方式）

1. **聚合器**：读全部角色 manifest → 按 `app` 分组 → 得出「需要哪几条通道连接、每条上哪些角色/群活跃」；
2. **平台进程内持有连接**：feishu-ingress / wecom-ingress 本就是 layer-infrastructure Provider（wecom-guide 已有进程内先例），每 app 一个连接实例，事件按声明路由到对应角色的 链路；
3. **部署 = 改声明**：加一个「机器人」= 加一份角色 manifest（或给既有角色加一段 channels 声明），聚合器热装配——**没有进程舰队、没有锁、没有启停按钮**；通道在线状态页显示的是「角色×通道在线矩阵」；
4. **运维件回归最小**：独立进程形态（过渡期）保留 start/stop 脚本 + 状态徽标；收口完成后这些随进程一起消失。

## 四、现实约束与已决事项

| # | 事项 | 状态 |
|---|---|---|
| 1 | **面貌 = 本体**（基线 2/4 已决） | 一角色一平台一 app；每个平台上的注册信息（头像/名字）都按角色设定——「上外勤」的部署动作含各平台 app 配置核对（平台做「面貌一致性」检查项：app 名/头像与角色 identity.name 比对提醒） |

| 3 | **跨位置/跨平台记忆**（基线 3/4 的技术落点） | TiMEM memory agent 按 `role.id` 归集：现状网页 persona 走 workflow-engine agent_id（=aigility-skill-\<id\>）、feishu-dsh 走 dsh-headless 自己的会话——**M1 必须统一到 role.id**，否则「同一个人」在数据层不成立 |
| 4 | ~~对端用户跨平台归集~~ → **已决（基线 5）** | 归集 + 页面可配，方案见 §四·补「人员身份中心」；数据模型 M1 定（与 TiMEM user_id 对齐），页面 M2 |
| 4 | **dsh-headless 桥特例** | feishu-dsh 中继到官方 dsh CLI 会话——收口后成为平台的「DSH 会话桥」模块（action 层管子进程），角色声明 `actions.engine: dsh-headless` 即委托；其会话记忆并入 role.id 归集 |
| 5 | **task-loop 归属** | 任务抽取逻辑 → 应用包化候选；播报能力 = outbound.push 的第一个实例 |
| 6 | **崩溃隔离** | 平台进程内多通道：handler 全量 try/catch 纪律 + 全局兜底；平台重启=全通道重启（对比独立进程损失重启粒度——收口的代价，需接受） |
| 7 | **纯网页/后台角色**（基线 1 已决） | 无 channels 段即不参与通道聚合；角色清单页区分 presence 标注（web / im / both） |

### 本文增量（对齐后的真实缺口）

1. **wecom 轴**：登记表现只有 feishu/gitea/timem 三轴——wecom 五 bot 收口后需加 `wecom_user_ids` 轴（identity-registry 加一轴，schema 向后兼容）；
2. **web 轴**：平台登录账号（AppBase users 邮箱）作为第四轴——网页内勤对话的 user_id 解析锚点；
3. **通道事件解析接线**：聚合器/通道收口后，事件带 `(platform, platform_uid)` 一律经 identity-registry 解析到 timem user_id 再进记忆（未命中走 auto-match 候选，不打断对话）；

## 六、治理对齐

- **收口支柱**：角色声明聚合后，外部信号真正只走平台唯一入口，旁路清零（M4 验收）；
- **可审**：每次通道事件按角色→user_key 归集计量与审计（现状独立进程各自为政）；
- **授权**：谁可改角色 manifest → 角色能力页（已有）+ r-admin 语义；
- **可换**：manifest 是声明，通道 Provider 可换（feishu/wecom/未来通道），「契约是主体」在通道层的表达。
