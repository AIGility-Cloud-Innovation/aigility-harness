# 项目小助理 · 数据对齐与记忆设计（2026-09-30 落地）

> 阶段目标：项目小助理能对齐不同的**项目**和**人员**，把飞书群消息、飞书私聊、
> 飞书任务清单、Gitea 工单、Gitea PR、timem 记忆、运维日志（log-monitor）七类
> 来源的数据妥善汇总判断；并定期把关键信息写入 timem 作为参考数据。
> 最终目标：每个人都能与小助理聊天获得自己的任务安排、给小助理做反馈；
> 小助理本身不做任务执行。

## 一、命名空间两维模型（纪律）

记忆命名空间 = `(user_id, agent_id)` 二元组，两个维度各管一件事：

| 维度 | 取值 | 纪律 |
|---|---|---|
| `agent_id` | 恒为 `feishu-task-assistant`（项目小助理） | 区分**不同 agent/场景**；新代码禁止漏传 |
| `user_id` | 只标识**人**：登记成员 = `timem_user_ids[0]`（真身太忆云账号，将来可在太忆空间看到自己的记忆），缺失回退 `member_id`；未登记来源回退**来源键**（如飞书 open_id） | 同一自然人跨来源必须是同一 user_id；**绝不用裸 `anonymous`** |
| 项目级记忆 | 虚拟用户 `project:<project_id>` + `domain=<project_id>` | 项目进展快照存这里，聊天时与人视角一起召回 |

明确否决过的方案：把 agent 维度编进 user_id（如 `wecom-timem:<userid>`）——
那会把同一个人在不同场景的记忆永远隔死，也让跨来源归一变得不可能。

## 二、两张对齐登记表（single source of truth）

均位于仓库 `config/`，带 `$schema` 说明文档，mtime 缓存自动重载——
平台页面改完，运行中的小助理下一次调用即生效，无需重启。

### 1. 人员：`config/timem-team-registry.json`（v2）

- 每个成员三条身份轴：`timem_user_ids` / `feishu_open_ids` / `gitea_usernames`，
  配套 `match_source`（`manual`=人工确认，`auto`=自动匹配待确认）。
- 解析与绑定纯函数在 `packages/layer-orchestration/src/identity-registry.ts`
  （同轴同 id 绑他人会抛错——防串号；自动匹配永不覆盖 manual）。
- 向后兼容：team-memory-console 的 TeamRegistry 继续可用（新增字段对它透明）。

### 2. 项目：`config/project-registry.json`（v1，新建）

- 每个项目登记：`gitea_repos` / `gitea_orgs`（整组织）/ `feishu_chat_ids` /
  `log_sources`（log-monitor 的 `{host,p,s}` 监控项）。
- **飞书任务清单不单独登记**：沿用既有约定「一个 Gitea 组织 = 一个清单」
  （`tasklistNameForRepo`），任务标题 `[org/repo#N]` 前缀反查仓库归属。
- 初始草案（2026-09-30 决策）：`nx-telecom`（群+2 仓库）、`timem-platform`
  （群+4 仓库+日志 timem-space_main）、`timem-ai-org`（org 展开全景）；
  hire_web 只有日志，暂缓立项。

## 三、人员自动匹配 + 平台审查页

流程：**先全自动匹配，再人工核对**（用户拍板）。

- 候选拉取：Gitea `/orgs/{org}/members`（组织来自项目登记表）+
  飞书通讯录 `contact/v3`（需应用通讯录权限，失败降级为仅 Gitea 并如实提示）。
- 打分（`scoreIdentityCandidates`，纯函数可单测）：完全一致 100 分；
  互相包含（≥3 字符）70 分；前缀 50 分。
- **≥70 分自动绑定为 `auto` 待确认；50-69 分只列为建议；manual 永不被覆盖。**
- 平台「身份对齐」页（`app/src/pages/IdentityPage.tsx`，模块 id `identity`）：
  一键自动匹配 → 逐条核对（采纳建议 / 手动绑定 / 解绑 / ✅确认），
  后端 API `GET /api/aigility/identity/overview`、
  `POST /api/aigility/identity/auto-match`、`POST /api/aigility/identity/bind`
  （实现 `examples/aigility-platform/src/identity-manager.ts`，写回原子替换）。

## 四、多源汇总：`@orchestration/project-briefing`

单服务四种模式（`packages/layer-orchestration/src/project-briefing.ts`）：

| 模式 | 数据源 | 命名键 |
|---|---|---|
| `person-brief` | Gitea 工单（执行/我提出）+ open PR（我的）+ 飞书任务（描述含「执行者：姓名」约定）+ timem 记忆召回 | 本人 timem id |
| `project-brief` | 项目四源：工单/PR + 飞书任务分组 + log-monitor 异常 + 项目记忆 | `project:<id>` |
| `feedback` | 反馈写入 timem（本人名下，可关联项目 domain） | 本人 timem id |
| `write-digest` | 项目快照 + 个人快照批量写入 | 如上 |

- 全部来源**尽力而为**：单源失败不阻塞其余，失败原因在回复尾部如实列出。
- 飞书任务按人切片依赖既有约定：`安排执行者` 把「执行者：X」写进任务描述
  （task-issue-sync handleAssignExecutor）；任务 v2 列表接口不回执行人 id，
  这是当前数据形态下的可靠途径。

## 五、定时 + 事件写入 timem

- **每日定时**：`startBriefingDigestScheduler`（feishu-task-loop 装配），
  默认 18:30（`BRIEFING_DIGEST_TIME` 可改，`BRIEFING_DIGEST_ENABLED=0` 关闭）；
  进程启动晚于触发点时当日补跑一次。每项目一条进展快照 + 每人一条个人快照
  （无在办事项时不写空个人快照）。
- **事件补充**：task-issue-sync 在 建单（手动/澄清归属）、工单关闭（PR 合并）
  三个点调用 `notifyRepoActivity` → `briefing-events` 按项目键 10 分钟前沿节流
  → 装配层 sink 调 `write-digest {trigger:"event"}`。

## 六、聊天入口（feishu-task-assistant v1.5.0）

| 说法 | 行为 |
|---|---|
| 我的任务 / 我的安排 / 任务安排 / 工作安排… | 人视角全景汇总（briefing；不可用时回落原飞书任务列表，不比改动前差） |
| 项目进展 [名称] / 进展汇报 … | 项目四源进展 |
| 反馈：<内容> / 建议：<内容> | 写入 timem 并确认（裸「建议」不触发，避免误收任务建议） |
| 帮助文本 | 已补三类新指令 |

## 七、边界与后续

- 飞书群历史消息未接（全仓无 `GET im/v1/messages`）：群消息维度暂只影响
  实时链路，不参与汇总；接历史拉取后可在项目快照里加「本周群讨论要点」。
- Gitea PR 无详情/review 状态（仅列表 + merged 判定）；PR↔工单关联靠 `#N` 文本。
- log-monitor 数据是「最近 N 行文本」而非结构化事件流，快照里只取 lastErr
  与最近错误行。
- timem 侧无记忆列表/按时间检索 API，召回全靠语义搜索（searchMemory）。
- hire_web 等日志-only 来源：登记表 schema 已支持（仅 log_sources 的项目条目），
  待有 gitea/群归属再立项。
