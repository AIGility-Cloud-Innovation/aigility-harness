## 待办一：给服务装一个"紧急刹车"

### 现在的问题（打个比方）

想象一个员工，负责守着一间办公室。

他推门进去，发现**门从里面锁着**（别人在用），于是退出来。但他**没有任何等待机制**——退出来立刻又去推门，推不开又退出来，立刻又推……

**每 2 秒一次，一直推了 140 次。** 中间没有停歇，也不告诉任何人"我这里出问题了"。

今天系统上就是这样：`feishu-task-loop` 这个服务，每次启动都因为"位置被别人占了"而失败，失败后立刻重启，如此循环。

### 为什么这很糟

| 后果 | 说明 |
|------|------|
| **日志被刷爆** | 每次失败都写日志，真正的错误信息淹没在里面，排查困难 |
| **看不出问题严重性** | 它一直"在重试"，看起来像在努力，实际是无用功 |
| **拖累同一个机器** | 每 2 秒起一个进程 = 频繁抢占 CPU 和内存，影响旁边正常跑的服务 |

### 要装"刹车片"

现在的配置是：
```
崩溃了 → 永远立刻重试，不限次数
```

应该改成：
```
崩溃了 → 重试几次还是不行 → 停下，标红，告诉人"这里坏了快来看"
```

具体说，在服务配置里加两行：
- **观察窗口**：5 分钟
- **允许失败次数**：5 次

也就是说：**5 分钟内连续失败 5 次，就停下。** 不再疯狂重试，而是进入"坏了"的状态等人处理。

### 为什么我没直接改

这个配置在系统的服务文件里（`~/.config/systemd/user/` 目录），属于**系统级设置**。改错了可能影响其他服务，所以按约定我先不动，等你确认。

**要改的话我会给你一段可以直接粘贴的完整配置**，你贴进去、执行一条命令即可生效。

## 待办二：搞清楚"那些开关到底开没开"

### 现在的问题（打个比方）

你们家有好几处开关：**墙上一个、遥控器上一个、还有一个总闸**。

现在的情况是：**总闸那边只贴了两个标签，其他开关一个都没标。** 你不知道那些没标签的开关：

- 是**根本没这个开关**（功能压根没做）？
- 还是**开关在别处、默认就是开着的**？

今天排查时就卡在这儿——我看服务配置里只有两项（`NODE_ENV`、`WORKER_TEAM_TIMEOUT_MS`），但系统实际跑着一堆功能（任务扫描、障碍分析、自动派发……）。**这些功能到底是开着的还是关着的？凭什么开着的？我答不上来。**

### 为什么这是个真问题

不是现在坏了，而是**以后一定会坑人**：

- 哪天想把某个功能关掉，你**不知道去哪儿关**
- 哪天想确认某功能是不是真在跑，你**没法确认**，只能猜
- 换个同事来维护，他完全看不懂"这些功能是靠什么开起来的"

### 要做的事

把**每个正在生效的功能开关**都查清楚，并标注它的来源。理想状态下能一眼看到：

```
任务状态扫描      = 开     ← 来自代码默认值
障碍分析          = 开     ← 来自代码默认值
自动派发          = 关     ← 来自环境变量
工人超时          = 1小时   ← 来自服务配置文件
```

**关键在于最后一列**——"这个值是谁定的"。今天缺的就是这一列。

### 为什么我没直接改

因为得先**查证**才能改。要查的是：
1. 代码里这些开关的默认值分别是什么
2. 现在实际生效的跟默认值一致吗
3. 哪些开关应该显式写进服务配置（免得以后"看似关了其实还开着"）

这是**只读排查**，不动任何配置。查完给你一份对照表，你再决定哪些要显式写进去。

## 两个待办的优先级

| | 待办一（紧急刹车） | 待办二（开关标注） |
|---|---|---|
| **紧急程度** | 较高 —— 防止下次再出现"140 次风暴" | 中等 —— 现在不坏，但迟早坑人 |
| **风险** | 低 —— 只是让失败时能停下来 | 零 —— 纯查证，不改东西 |
| **耗时** | 你贴一段配置即可 | 我需要查一轮代码 |
| **建议** | 优先做 | 可随后 |

---

## 一句话总结

- **待办一**：给服务装个刹车，别让它坏了还一直猛踩油门。
- **待办二**：把"哪些功能开着、凭什么开着"写成一张明白账。

两件事都是**为了让下次出问题时，人和 AI 都能一眼看懂，而不是靠猜。**
