# 智悦 · 插件与应用安装体系设计

> 版本：v0.1 ｜ 日期：2026-09-29 ｜ 状态：草案待审
>
> 定位：回答「**加什么插件就能变成什么工作台**」——把智悦做成装配台：不同的人上门，给他装几个插件、开几个应用、配一个预设，就是一个新工作台。报警系统（baojing-qa）是这套体系的首个完整实例。

## 一、结论

1. **平台已经有完整的插件运行时，缺的只是「安装入口」**：`dsh_plugins` PG 表就是插件注册表（config JSONB + enabled 开关），`dshLoadPlugin/dshUnloadPlugin` 支持热装卸（platform.ts 种子已在用）——把种子逻辑变成用户可操作的安装/启停/卸载 API，工具插件层即闭环。
2. **应用装配层有设计无实现**：`platform-module-plugin-design.md` Phase 0（模块注册表 + `app_modules`/`app_module_presets` 持久化）是「装应用」的底座，本期落地。
3. **开源优先的接入面就是 MCP**：dsh-mcp-client 已打通 stdio MCP server → ctx.tools → 工具总线，官方/社区 MCP server（filesystem、fetch、neo4j、postgres 等）即装即用，不需要为每个工具写代码。

## 二、三类可安装单元

| 单元 | 是什么 | 安装动作 | 生效方式 | 存储 | 现状 |
|---|---|---|---|---|---|
| **工具插件** | MCP server、DSH 官方工具包 | 插件中心安装表单（包名/命令/参数） | **热装载**（dshLoadPlugin，不用重启） | `dsh_plugins` 表 | 运行时真，安装入口本期补 |
| **应用（页面模块/应用包）** | 导航板块集合 + 预设 | 模块装配开关 / 套用预设 | 导航显隐 + 路由守卫即时 | `app_modules`/`app_module_presets` 表 | 导航机制真（enabledModules），持久化本期补 |
| **智能体（技能）** | Prompt 人设 + 能力声明 | 工厂发布 / 模板挑选 | 发布即可对话 | `data/aigility-skills.json` | **已闭环**（skill-registry） |

引擎能力插件（LayerPlugin/py-bridge）保持代码级/声明式装配（改代码或 py-plugins JSON + 重启）——那是**平台工程能力**，不是用户可操作单元；用户可操作层永远由上面三类构成，边界与「执行器路由 YAML 只声明数据面」同一哲学。

## 二·补、能力插件的板块归属（梳理结论 · 2026-09-30）

原则：**安装收敛在一个面，呈现分散到归属板块，应用与插件不混装。**

- **工具插件中心 = 唯一安装面**：所有能力插件（MCP server / 官方 DSH 行 / 第三方社区插件）的安装、启停、卸载、审计只在此发生——单一入口、单一审计；
- **呈现按归属分散**：装完的能力在其业务板块出现（见下表右列），挂接随该板块接真逐个补，不为插件单开板块；
- **不混装**：模块装配（页面板块）与应用中心（场景应用）不是插件——它们是插件与模块组合出的工作台形态，边界即 manifest 的 `kind` 字段。

| 插件类别（社区 Hub 分类归并） | 安装面（唯一） | 装完在哪呈现/生效 |
|---|---|---|
| Tools & Capabilities（web/文件/shell/DB） | 工具插件中心 | 工具总线（ctx.tools）+ 数字员工对话可调用 |
| Integrations & Connections（MCP/通知/协议桥） | 工具插件中心 | 工具总线；通知类 → 工作台消息卡 |
| Memory & Context（压缩/召回/持久化） | 工具插件中心 | 对话链路行为；「角色能力 · DSH」可见 |
| Skills & Agents | 工具插件中心 | 角色能力·DSH 技能货架 → 智能体市场上架 |
| Workflow & Automation（审批/编排） | 工具插件中心 | 任务板人审回路 |
| Models & Reasoning（路由/代理/成本） | 工具插件中心 | 模型管理 |
| Data & Knowledge（检索/知识库/图谱） | 工具插件中心 | TiMEM 空间 / 知识图谱 |
| Dev & Ops（诊断/健康面板） | 工具插件中心 | 运营驾驶舱 |
| UI & Experience（主题/皮肤） | 工具插件中心 | 平台配置 |
| Entertainment | 工具插件中心 | 不自挂板块 |

## 三、开源优先映射

| 需求 | 现成开源工具 | 接入方式 |
|---|---|---|
| 工具生态（文件/网页/数据库/图查询…） | MCP 官方与社区 server（`@modelcontextprotocol/*`、`mcp-neo4j-cypher`、`mcp-server-fetch` 等） | 插件中心装一条 dsh-mcp-client 行（command/args 即声明），零代码 |
| 图数据库 | Neo4j Community | docker-compose 加服务；走 MCP server 或 @action 插件 |
| 关系库 / 账号 / 计量 | PostgreSQL（已在） | AppBase 单库多职 |
| LLM 网关 | LiteLLM（已在，38 模型池） | env 即接 |
| 可视化 | ECharts / AntV / three.js（已在） | 前端现用 |
| 表格导入 | SheetJS（xlsx）或 openpyxl（py-bridge） | 数据导入插件 |
| 文档产出 | docx（doc-worker 已用） | 现用 |

原则：**优先「装现成的」，其次「写一条 YAML/一行声明」，最后才写代码**。任何需要写代码才能接入的工具，先看它有没有 MCP server。

## 四、本期补齐的缺口（实施清单）

> **落地状态（2026-09-29）**：4.1 与 4.2 已实现并通过 typecheck/build——后端 `platform.ts`（`app_modules`/`app_module_presets` 建表 + `SERVER_MODULE_META` 校验 + dsh_plugins 读写辅助）、`index.ts`（modules/presets/plugins 三组 API + 审计）、前端（`app/src/modules/registry.ts` manifest 迁移、harness.ts 客户端、App.tsx 登录后拉装配状态、ModulePage 预设接真、ToolsPage 已安装插件区块）。重启服务后生效。

### 4.1 工具插件安装层（后端 + 插件中心）✅ 已落地

| 接口 | 说明 |
|---|---|
| `GET /api/aigility/plugins` | dsh_plugins 全表 + dshStatus 运行态（装载时间/错误） |
| `POST /api/aigility/plugins` | 安装：`{name, package, export_name?, description?, config?, enable?}` → 插行 → 热装载 → 审计（MCP server 即一条 `dsh-mcp-client` 行） |
| `PUT /api/aigility/plugins/:name` | 启停：更新 enabled → 装载/卸载 → 审计；`system-prompt`/`tools` 为平台关键件，禁停 |
| `DELETE /api/aigility/plugins/:name` | 卸载：热卸 → 删行 → 审计；关键件禁删 |

前端：工具插件中心新增「已安装插件」真区块（清单 + 运行态徽标 + 启停/卸载 + MCP 安装表单），替代原「插件开关 Mock」。

### 4.2 应用装配层 Phase 0（模块装配真化）✅ 已落地

按 platform-module-plugin-design §4-§5 实施：`app/src/modules/registry.ts`（manifest 随代码评审）+ `app_modules`/`app_module_presets` 表 + `GET/PUT /api/aigility/modules`、presets 三组 API（会话校验 + `module.toggle`/`preset.apply` 审计）+ App.tsx 登录后拉取装配状态（localStorage 降级为离线缓存）+ ModulePage 接真（「保存为项目模板」真化）。项目小助理的导航开关（TaskLoopConfigPage ↔ enabledModules）自动随新底座工作，无需改动。

### 4.3 预设即工作台

- 种子预设 `default`（全部可用模块开）；
- 「给某类人配一个工作台」= 建一个预设（模块组合）→ 套用；后续接租户/用户绑定（P2，本期全局单套）。

## 五、baojing-qa = 首个完整安装清单（示例）

给一个化工客户装「报警分析工作台」：

```
① 装插件 ×2
   - 报警数据插件：PG alarm_log 表 + Excel 导入 + 查询执行（@action/alarm-query）
   - 图谱插件：docker 起 Neo4j → 插件中心装 mcp-neo4j-cypher（或 @action/baojing-graph）
② 装应用 ×1（应用包「报警分析」= 预设 baojing-qa）
   - 开：报警看板 / 报警数据 / 知识图谱 / 数据导入（+ 既有的数字员工、任务板）
   - 关：与场景无关的演示板块（按需）
③ 配技能 ×1
   - 工厂发布「报警分析助手」（意图路由 YAML + 36 SQL 模板随技能版本化）
④ 配数据源 ×1
   - Neo4j 连接（插件中心配置）+ 报警库（默认平台 PG）
```

四步之后客户得到一个完整工作台，全程无代码——这就是「装什么插件就变成什么工作台」的验收标准。

## 六、治理与边界

- 插件安装/启停/卸载、模块开关、预设套用全部入 `audit_log`（actor=登录邮箱）；
- `core` 模块服务端拒关；`system-prompt`/`tools` 关键插件拒停拒删；
- 谁可以装插件/改装配：对齐 app-permission-design 的 r-admin 语义（本期管理员全权，权限矩阵接真后收口）；
- 插件安装不解决供应链治理：包名即 `npx` 拉取，沙箱与审计依赖 dsh-interop 既有约束（G2 生产级治理范畴）。
