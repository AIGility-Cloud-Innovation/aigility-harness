# aigility-harness · 启动与部署指南

> **第一部分**：本机日常启动速查（平时看这里）；**第二部分**：端口与环境变量配置参考；**第三部分**：从零部署踩过的坑 + 换机迁移最短路径。

## 一、日常启动（本机，Windows + 原生 PG）

> 2026-09-14 实测记录。本机为 **Win10 + 原生 PostgreSQL 15**（数据目录 `D:\DATABASE`，端口 **5432**，非 Docker 方案；Docker 方案见第三部分坑 3）。

### 启动

1. 确保 PostgreSQL 在跑（本机 PG 未注册自启服务，需手动拉起）：
   ```bat
   "C:\Program Files\PostgreSQL\15\bin\pg_ctl.exe" -D "D:\DATABASE" -l "D:\DATABASE\log\manual-start.log" start
   ```
   验证：`Test-NetConnection 127.0.0.1 -Port 5432` 为 True。
2. 双击 `examples/appbase/start-appbase.cmd`
   （首次使用：从 `start-appbase.cmd.example` 复制一份，填好 `BIGMODEL_API_KEY` 等标记项；该脚本含密钥，已被 .gitignore 忽略。**本机为原生 PG 5432，脚本里必须设 `APPBASE_PG_PORT=5432`**——代码默认值是 5433，别漏）。
3. 拉取新代码后先在仓库根目录 `pnpm install` 再启动（新增 workspace 包如 `@aigility-harness/layer-action` 不装会报 `ERR_MODULE_NOT_FOUND`）。
4. 控制台出现 `AppBase 已就绪` 即可：
   - 本机：<http://127.0.0.1:1231/hall>
   - 局域网设备：`http://<本机局域网IP>:1231/hall`（IP 用 `ipconfig` 实查，别用 172.x 虚拟网卡地址）

### 服务与地址

| 服务 | 地址 |
|---|---|
| 应用大厅（hall） | <http://127.0.0.1:1231/hall> |
| 具体应用页面（examples/apps 下的 HTML） | `http://127.0.0.1:1231/apps/应用名.html`（如 `teacher-notebook.html`） |
| 后端 API | <http://127.0.0.1:1231/app/apps> |
| AI 网关（需 Bearer 鉴权，密钥见 start-appbase.cmd 的 `APPBASE_GATEWAY_KEY`） | <http://127.0.0.1:1232/v1/chat/completions> |

### 常见排查

| 症状 | 处理 |
|---|---|
| 启动即失败、连不上库 | PG 没跑：`pg_ctl -D D:\DATABASE start`（见上方启动第 1 步） |
| 报错 `数据库 "appbase" 不存在`（3D000） | 5432 被**别的 PG 实例**占了。本机曾出现安装器注册的 Windows 服务 `postgresql-15`（用全新空数据目录 `C:\Program Files\PostgreSQL\15\data`）抢注 5432：先停掉它（`net stop postgresql-15`，需管理员）再手动挂载 `D:\DATABASE` 启动。**根治**：`sc config postgresql-15 start= demand` 把空服务改为手动，否则每次开机复发 |
| 1231/1232 被占（重复启动会这样） | `netstat -ano \| findstr 1231` 找 PID，`taskkill /PID <pid> /F` 后重启 |
| `ERR_MODULE_NOT_FOUND: @aigility-harness/layer-action` 等包 | 拉了新代码没装依赖：仓库根目录 `pnpm install` |
| 启动报 `字段 "app_id" 不存在`（42703） | 老库表结构与新代码不一致（如 `app_members` 旧列名 `app_name`）。确认表无数据后可 drop 重建为新结构；`CREATE TABLE IF NOT EXISTS` 不会改已存在的表 |
| 对话/AI 报“该应用尚未配置 LLM" | start-appbase.cmd 里 `BIGMODEL_API_KEY` 没填 |
| 其他设备打不开页面 | 防火墙规则 "AppBase 1231/1232" 是否还在（`Get-NetFirewallRule -DisplayName 'AppBase*'`）；访问地址用的是否本机真实 IP |
| 应用换设备数据不通 | 应用的 API 基址被硬编码了，见第三部分坑 5 |
| 重启后要重新登录 | 一般不会（token 密钥持久化在 `examples/appbase/src/.token-secret`）；除非删了该文件或改了 `APPBASE_TOKEN_SECRET` |

### 企微机器人接入 DSH（wecom-dsh，2026-09-17 实测全链路打通）

链路：企微群 @机器人 → `examples/wecom-dsh`（`wecom-ingress` WebSocket 长连接）→ 官方 `dsh --profile headless` CLI（每条消息一个独立 headless 进程；headless 无 `--resume` 续聊，多轮对话由中继的滚动上下文注入实现，见 `examples/wecom-dsh/README.md`）。

启动步骤：

1. 企微管理后台 → 「智能机器人」→ 创建，拿到 botId + secret。
2. 配置填在 **`examples/wecom-dsh/.env`**（gitignored，模板 `.env.example`）：`WECOM_DSH_BOT_ID` / `WECOM_DSH_BOT_SECRET` / `DSH_BIN` / `DSH_HOME` / `DEEPSEEK_API_KEY` / `DEEPSEEK_BASE_URL`。**不放仓库根 `.env`**——dsh 的保留变量检查会拒绝（见坑 9），放示例自己的目录则不受约束、可直接用真名。
3. `DSH_BIN` 指向官方 dsh 的 `lib/bin.js` 绝对路径，真实 hash 用这条命令查：
   ```powershell
   node -e "console.log(require.resolve('@deepseek-ai/dsh/package.json'))"
   # bin.js 在所得路径同目录的 lib\bin.js
   ```
4. 启动：`pnpm --filter wecom-dsh start`；企微群里 @机器人 说话即通。`/new` 清空对话历史、`/session` 看保留轮数。
5. 先单独验证 dsh 可用（免去企微变量干扰）：`$env:DSH_HOME=...; node <bin.js> --profile headless "回复ok"`。

#### 坑 9：dsh 禁止 `.env` 文件出现保留变量名（readEnvLayer 安全检查）

dsh-app-boot 的 `readEnvLayer`/`loadLayeredEnv` 会对工作目录逐层加载的 `.env` 文件做保留名单检查，命中即抛错退出：

```
Error: dsh: <路径>\.env sets "DSH_BIN", which only the launching environment may set ...; export DSH_BIN instead of putting it in a .env file
```

已确认的保留变量（决定进程怎么启动/代码从哪加载/走哪个网络，只允许环境变量注入）：`DSH_BIN`、`DSH_HOME`、`DEEPSEEK_BASE_URL`。`DEEPSEEK_API_KEY` 不在名单内，文件形式可用。

- **解法（推荐）**：这些配置不该放仓库根 `.env`，放到**调用方的自有配置文件**里（如 `examples/wecom-dsh/.env`，在 dsh 的工作目录加载范围之外），直接用真名，由调用方进程以环境变量传给 dsh 子进程。绝不要用"改名绕检"（如 `WECOM_DSH_BIN` 别名再映射回去）——那是绕补丁，配置含义失真且每来一个新保留变量就要加一条映射。
- 报错只报**第一个**命中的变量，修一个会再冒下一个（实测顺序：DEEPSEEK_BASE_URL → DSH_BIN → DSH_HOME），要全部挪出 `.env`。
- 任何在 dsh 工作目录（默认仓库根）下以 `dsh --profile headless` 跑任务的场景都受此检查约束，不只是企微入口。

#### 坑 10：PowerShell 里 `pnpm` 优先解析到 pnpm.ps1 被执行策略拦截

便携版 Node 目录里 `pnpm` 同时有 `.ps1`/`.cmd` 两个 shim，PowerShell 按 PATHEXT 优先选中 `.ps1`，默认执行策略（Restricted）直接拒绝：

```
pnpm : 无法加载文件 ...\pnpm.ps1，因为在此系统上禁止运行脚本
```

- 一次性解法（推荐）：`Set-ExecutionPolicy -Scope CurrentUser -ExecutionPolicy RemoteSigned`（本地脚本放行、下载脚本仍需签名）。
- 不改策略：PowerShell 里用 `pnpm.cmd`，cmd 终端里 `pnpm` 不受影响。

### 备份

> 注意：`scripts\backup-appbase.cmd` 与每日计划任务 "AppBase Daily Backup" 是 **Docker PG（appbase-pg 容器）时代的产物**，本机现为原生 PG，该脚本会失败，待改造。

- 本机手动备份（原生 PG）：
  ```bat
  set PGPASSWORD=<密码>
  "C:\Program Files\PostgreSQL\15\bin\pg_dump.exe" -h 127.0.0.1 -U postgres -d appbase -Fc -f D:\AppBaseBackups\appbase-%DATE%.dump
  ```
- 恢复（原生 PG，恢复前确认 PG 在跑且 appbase 库存在）：
  ```bat
  "C:\Program Files\PostgreSQL\15\bin\pg_restore.exe" -h 127.0.0.1 -U postgres -d appbase --clean <dump文件>
  ```
- 别忘了 `examples\appbase\src\.token-secret`（丢了所有登录态失效），可随备份一起拷贝。

## 二、配置参考：端口与环境变量

`examples/appbase/start-appbase.cmd`（真身不入库，模板 `start-appbase.cmd.example` 入库）统一设置这些。

### 端口约定

- PG：本机 Docker 容器映射到**宿主 5433**，与代码默认值（`examples/appbase/src/backend.ts` 的 `APPBASE_PG_PORT ?? 5433`）对齐，因此本机**无需**设 APPBASE_PG_PORT。原生 PG 跑在默认 5432 的机器上，必须设 `APPBASE_PG_PORT=5432`——别假设代码默认值就是实际端口。
- AppBase 主服务 1231（hall + 后端 API，同源）。
- AI 网关 1232（Bearer 鉴权）。

### 必需的环境变量（缺了各自的失败表现）

| 变量 | 作用 | 缺失表现 |
|---|---|---|
| `APPBASE_PG_PASSWORD` | PG 连接密码（本机=容器 POSTGRES_PASSWORD） | 启动即失败（initAppBackend 连不上库） |
| `APPBASE_PG_PORT` 等 | PG 连接（host/port/user/db） | 本机默认值即可；原生 5432 的机器必须设 PORT=5432 |
| `BIGMODEL_API_KEY` | LLM 上游 | 页面能开，对话/AI 功能报"该应用尚未配置 LLM" |
| `AGENT_DRIVER=zcode` | 网页应用开发员驱动 | 默认走 codex；本机 zcode/codex 都装了，脚本默认 zcode |
| `APPBASE_GATEWAY_KEY` | 网关鉴权 | 不设则每次启动随机生成打印在控制台（外部调用方要跟着换） |
| `APPBASE_TOKEN_SECRET` | 登录 token 签名 | **不设也没事**：代码会生成随机密钥持久化到 `examples/appbase/src/.token-secret`（gitignore），重启登录不失效 |
| `APPBASE_ADMIN_EMAILS` | 管理员邮箱白名单（逗号分隔，可选） | 不设时首个注册用户自动成为管理员；也可 SQL 提拔 `UPDATE users SET is_admin=true WHERE email='...'` |

### 自启情况

- PG：Docker 容器设了 `--restart unless-stopped`，Docker Desktop 自启时随起（前提：Docker Desktop 设置了开机自启）。
- AppBase：仍为手动，用一键脚本（脚本会先确保 PG 容器在跑）。

## 三、换机部署与坑点

记录本项目在 Windows 上从零部署踩过的坑，供迁移到其他服务器时参考（2026-09-08 入库并按当前机器现状更新；原为散逸文档，不入库换机即丢）。

### 环境安装的坑

#### 坑 1：Node.js 用 MSI 安装会卡 UAC

winget/MSI 静默安装会触发 UAC 弹窗，无人值守场景会永久挂起。
解法：用官方 zip 便携版（node-vXX-win-x64.zip）解压即用，手动加 PATH。

**便携版 Node 必须真的进 PATH，否则 `pnpm install` 会半途而废。** 症状很有迷惑性：用完整路径调
`& "D:\SiteWorkspace\tools\node-v24.19.0-win-x64\pnpm.cmd" install` 时，pnpm 自己照样能跑——因为 `pnpm.cmd` 里有
`IF EXIST "%dp0%\node.exe"` 的回退，会直接用同目录的 node.exe。但依赖的 `postinstall` 脚本是从 **PATH** 找 `node` 的，
于是全部报 `'node' 不是内部或外部命令`（GBK 控制台下显示成乱码 `'node' �����ڲ����ⲿ���`，容易看成脚本本身坏了）。

- **后果不只是"几个脚本失败无所谓"**：pnpm 在生命周期脚本阶段抛错后，**不会继续链接 `node_modules/.bin`**，
  整个 install 以 exit 1 收尾。表现是 `node_modules/.pnpm/` 里包都在、但根 `node_modules/.bin/` **目录根本不生成**，
  `tsc` / `tsx` / `vitest` 全部不可用。（判断安装是否真的完成，看 `.bin` 而不是看包的数量。）
- 修法：`scripts\add-node-to-path.ps1`，把便携版 Node 目录写进**用户级** PATH（先备份原值到 `.workbuddy\tmp\env-backup\`，
  保留 `REG_EXPAND_SZ` 值类型，不截断不排序不覆盖原有条目）。
  ```powershell
  powershell -ExecutionPolicy Bypass -File scripts\add-node-to-path.ps1
  ```
  已打开的终端不会自动生效，必须**新开**一个 PowerShell。移除用 `-Remove`。
- 临时应急（完全不碰注册表）：在当前 PowerShell 里 `$env:Path = "D:\SiteWorkspace\tools\node-v24.19.0-win-x64;$env:Path"` 后再跑 pnpm。
- **可容忍的失败**：`ffi-napi@4.0.3` / `ref-napi@3.0.3` 会报 node-gyp
  `You need to install the latest version of Visual Studio`——它们是 `vosk`（layer-persona 的 optionalDependencies）
  的下游，pnpm 会 `skipped as optional`，不影响 exit code，也**不需要**为此装 VS。

**pnpm 版本要对齐 ≥10.26。** 仓库 `pnpm-workspace.yaml` 用了 `allowBuilds`（v10.26.0 引入，替代 `onlyBuiltDependencies` / `ignoredBuiltDependencies`）和 `minimumReleaseAgeExclude`（10.x 引入，用于把个别包排除在 `minimumReleaseAge` 冷却期外；当前工作区只配了排除清单，未启用冷却期本身）。低于该版本时这些字段会被**静默忽略**：

- `allowBuilds` 不生效 → 构建脚本白名单失效。pnpm 9 默认放行所有依赖的 `postinstall`，于是 `msedge-tts` / `ffi-napi` / `ref-napi` / `onnxruntime-node` / `sharp` 多跑一批本该跳过的构建（`esbuild` 本来就需要构建，无影响）。
- 注意 `engines.pnpm` 目前写的是 `>=9.0.0`，与配置实际要求不符，是历史遗留；换机时按 10.26+ 装更稳。
- 实践上不致命：带原生编译的 `vosk` 是 `packages/layer-persona` 的 `optionalDependencies`（lockfile 标 `optional: true`），其子依赖 `ffi-napi` / `ref-napi` 构建失败会被容忍，不会中断整个 install。
- 升级前留意 lockfileVersion（当前 `9.0`），pnpm 10.x 沿用 9.0，不要直接跳到大版本以免被改写。

#### 坑 2：pnpm install 需要访问私有 Git 仓库

依赖 `@timem/dsh-plugin-timem` 来自私有 Gitea（git.aigility.cloud，GitHub 镜像同样私有），匿名访问 401。仓库里 4 处声明指向同一仓库（`packages/layer-cognitive`、`examples/appbase`、`examples/dsh-timem-demo`、`examples/wecom-timem`），写法都是 `git+https://git.aigility.cloud/TiMEM-AI/dsh-plugin-timem.git`。

报错形态：`remote: Failed to authenticate user` 折成 `fatal: Authentication failed for 'https://git.aigility.cloud/TiMEM-AI/dsh-plugin-timem.git/'`，pnpm 再包一层 `Command failed with exit code 128`。

**方案 A（推荐，非交互）：让 git 把 HTTPS 透明改写成 SSH。** 前提是该主机已配好 SSH key（`~/.ssh/id_ed25519`，公钥已录入 Gitea）——主仓本身就用 `ssh://git@git.aigility.cloud:1022/...` 拉取，能推能拉即满足。

```bash
git config --global url."ssh://git@git.aigility.cloud:1022/".insteadOf "https://git.aigility.cloud/"
```

- 只改本机全局 git 配置，**不动仓库**，队友不受影响；`url.insteadOf` 由 git 自身在 clone 前改写，pnpm 无需任何额外参数。
- 验证：`git ls-remote https://git.aigility.cloud/TiMEM-AI/dsh-plugin-timem.git` 能列出 refs 即通。（验证过：改写后该命令返回 `refs/heads/main`。）
- 撤销：`git config --global --unset url."ssh://git@git.aigility.cloud:1022/".insteadOf`

**方案 B（需要人工点一次）：HTTPS + Git Credential Manager。**

- 必须先装 Git（本机用便携版 PortableGit）。
- 首次拉取时 GCM 弹凭据助手选择框（选 manager 并勾选"始终使用"），随后浏览器弹 Gitea OAuth 登录页，人工登录一次，之后凭据缓存到 Windows。
- **坑**：一旦选了凭据助手但没走完登录，GCM 不会再弹，只会一直 `Failed to authenticate user`。此时先 `git credential-manager clear`（或删掉 Windows 凭据管理器里 `git:https://git.aigility.cloud` 那条）再重试。
- 无 git 时报错是 `ENOENT not found: git`，容易误判为网络问题。

**其它**

- lockfile 把该依赖钉在 `7eaed2e3a78217d99a81e1ad88961bb11bf3c0e4`，远端仍在（`git fetch <ssh-url> <sha>` 可取到），不必担心需要重新解析版本。
- pnpm 在安装/校验 store 时会在项目根目录建一个 0 字节探针文件 `_tmp_<pid>_<hash>`（用于判断 store 是否位于 home 下），正常会自动删掉；若被沙箱或杀软拦住删除会留下残留，无害，手动删即可。

#### 坑 3：PostgreSQL 部署

**本机方案（当前）：Docker。** 容器 `appbase-pg`（postgres:16-alpine），宿主 5433 → 容器 5432，数据落在 named volume `appbase_pg_data`，`--restart unless-stopped` 随 Docker Desktop 自启。一条命令即可在任意有 Docker 的机器重建：

```
docker run -d --name appbase-pg --restart unless-stopped \
  -e POSTGRES_USER=postgres -e POSTGRES_PASSWORD=<密码> -e POSTGRES_DB=appbase \
  -p 5433:5432 -v appbase_pg_data:/var/lib/postgresql/data postgres:16-alpine
```

**别的机器按实际环境选**。原生安装的历史经验（曾在旧机用到）：

- 旧机曾只剩数据目录 D:\DATABASE（PG 15）而程序被卸载。解法：重装同大版本二进制，`pg_ctl -D 数据目录 start` 直接挂载旧数据目录，数据无损。
- 安装器自建的默认实例服务会占用 5432 并使用自己的空数据目录，需停掉并设为手动启动，再挂载旧目录。

#### 坑 4：旧 PG 密码未知时的重置办法（Windows，原生安装适用）

1. 备份 pg_hba.conf；
2. 在文件顶部临时加一行 `host all postgres 127.0.0.1/32 trust`；
3. **注意用无 BOM 的 UTF-8 写入**（PowerShell Out-File/Set-Content 默认带 BOM，会导致 PG 报"无效连接类型"拒绝启动，本机踩过）；
4. `pg_ctl reload` 后免密登录，`ALTER USER postgres PASSWORD '...'`；
5. 恢复原 pg_hba.conf 并 reload。

### 多设备/局域网的坑

#### 坑 5：生成的前端应用曾硬编码 127.0.0.1（已根治，注意复发）

teacher-notebook 等 AI 生成应用曾把 API 基址写成 `http://127.0.0.1:1231`，导致其他设备打开页面时请求打到设备自身，表现为"换设备要重新建账号、数据不共享"。

已落地的根治（2026-09-08）：

1. 生成器提示词（`packages/layer-persona/src/app-dev.ts` 的 APP_DEV_SYSTEM_PROMPT）明确要求：后端 API 一律相对路径（空基址）、禁止硬编码 127.0.0.1/localhost/内网 IP/端口；直连网关用 `location.hostname` 动态推导。
2. `examples/apps/teacher-notebook.html` 三处硬编码回退已改为：API 基址默认同源相对路径；网关地址用 `location.protocol + '//' + location.hostname + ':1232'` 推导；历史 localStorage 里存的 127.0.0.1 地址一律视为过期忽略。

注意复发：新生成的应用若又出现绝对地址，说明提示词被冲掉，回看本条。

#### 坑 6：多设备账号语义

- 账号体系是全局的（存服务端 PG users 表 / app_accounts 表），所有设备共享。
- 每台设备首次访问需登录一次（token 存各设备浏览器），用同一账号登录即见同一份数据——不需要重新注册。
- 大厅管理抽屉里「登录」和「注册并登录」按钮并排，手机上容易点错成注册，产生多余账号（误建的可用 SQL 清理：`DELETE FROM users WHERE email='...'`）。

#### 坑 7：局域网/防火墙

服务监听 0.0.0.0，但 Windows 防火墙默认拦入站。其他设备访问前需放行 1231 和 1232（应用直连网关需要）：

```powershell
New-NetFirewallRule -DisplayName "AppBase 1231" -Direction Inbound -Protocol TCP -LocalPort 1231 -Action Allow
New-NetFirewallRule -DisplayName "AppBase 1232" -Direction Inbound -Protocol TCP -LocalPort 1232 -Action Allow
```

设备访问地址：`http://<服务器局域网IP>:1231/hall`。IP 以 `ipconfig` 实查为准（旧机是 192.168.1.10，换机后勿沿用）；多网卡机器注意别用 172.x 这类 WSL/Hyper-V 虚拟网卡地址。

### 迁移到新服务器的最短路径

1. 装 Node ≥20（建议便携版）→ `npm i -g pnpm@9`；
2. 装 Git + 完成一次 Gitea OAuth 登录；
3. PG 二选一：有 Docker 就跑坑 3 的 `docker run`（最快）；没 Docker 就原生装 PG 15+ 建库 appbase；
4. 仓库根目录 `pnpm install`；
5. 复制 `examples/appbase/start-appbase.cmd.example` 为 `start-appbase.cmd`，填好【填】项，运行（或 `cd examples/appbase && pnpm start`）；
6. 防火墙放行 1231/1232（命令见坑 7），局域网设备用服务器实查 IP 访问；
7. 需要迁移数据时：带上 `D:\AppBaseBackups\` 最新 dump，恢复命令见第一部分「备份」。
